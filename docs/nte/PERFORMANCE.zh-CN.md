# 性能证据与口径

测试主角色：4080 SUPER 渲染游戏，RTX 5080 运行 NR。历史 COPY 对比为4K颜色、2562×1441引导、单次NR、强度/结构/肤色/色调2、风格1、AutoMask；游戏DLSS Quality。这些配置与日期不同的其他记录不能自动当作完全相同场景。

## 历史吞吐和COPY优化

| 记录 | 完整tuple / 连续间隔 | 唯一NR完成 /s | 全传输 elapsed ms | NR ms |
| --- | --- | ---: | ---: | ---: |
| M339c旧日志重解析 | 82 / 81 | 26.698760 | 7.073058 | 未用于此对比 |
| M340＋ForceTagging，2026-10-21 | 104 / 103 | 33.451161 | 6.012607 | 15.159885 |
| M341，2026-10-21 | 96 / 95 | 32.064379 | 5.502414 | 15.157783 |

M340历史对比的NR完成节奏上升25.29%，传输端点缩短1.060450ms；但**不是只改COPY的控制A/B**：ForceTagging和资源提交路径也变化，场景/温度/负载未独立控制。M341传输又减0.510194ms，NR几乎不变，但源周期变长，因此整体完成节奏下降，不能写成继续提帧。

M340全部104帧出现发送引导/接收颜色的正重叠；M341全部96帧出现发送运动/接收深度的正重叠。NR依然等完整输入。它们是GPU timestamp区间证据，可能包含依赖等待，并非专属硬件执行时间。

## 帧生成、手感与当前限制

### 第二张卡承担六倍FG时的基础帧观察

历史M343未开启FG时唯一NR节奏33.020313/s，M351六倍请求时真实源33.05/s、SDK194.85/s，M352则33.1/s、SDK195.2/s。因此可说**这些窗口没有观察到明显基础帧损伤，六倍主要利用副卡算力扩大输出**，但不同版本/窗口不是严格开关A/B，不能保证任意场景零开销。5080同时做NR与FG，资源COPY、退休、SDK节拍和源Reflex反馈仍可能影响源周期。完整[helper职责与性能边界](HELPER.zh-CN.md)。

最新组合的大采集：出站COPY bracket4.880ms、接收2.874ms、NR16.667ms、helper CPU0.360ms、Present API0.144ms、捕获到Present返回52.990ms。**阶段重叠，不能相加成一帧时间；52.990ms不是输入到光子。** 显示事件全部ComposedFlip/Application，不能当成每张生成帧的物理扫描时刻。

用户选择的干净游戏约40FPS（25ms）是参考观察，不是GPU纯渲染硬下限；单卡4080S NR约22–24FPS也是用户观察，缺少同场景受控对照。它们应与可解析的NR完成记录分别标注。

## 稳定性

R333直接shared capture曾将engine-frame槽位与accepted-seal槽位混用，跳帧后失配；历史26/26传输样本发现错位，不能泛化成所有帧。后续保留统一身份、自有快照和退休保护。M340/M341/M342实测后用户确认画面稳定；不是对所有游戏和场景的保证。

M362用户确认输入解耦明显解决转动顿挫；随后的按钮/滚轮/光标问题由M363分层窗口穿透契约修复，软件和隐藏测试不等于所有真实输入验收。

M366曾获更流畅反馈但无明显基础帧增益，之后收到启动异常并回退；没有可用栈证明该改动是根因。M367从未部署。两者不在首发包内。
